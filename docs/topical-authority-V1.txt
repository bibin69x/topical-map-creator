**Version:** V1.0
**Status:** Build Specification
**Initial Market:** India
**Initial Price:** ₹199 Early Access
**Primary Goal:** Acquire the first 10,000 paying customers

---

## 1. Product Definition

### Product

A low-cost SEO tool that helps freelancers, SEO freshers, and digital marketing professionals create a structured **Topical Authority Map** for a website/topic.

### Core promise

> **Build a complete topical authority strategy without expensive SEO software.**

### The problem

SEO beginners and freelancers understand that topical authority matters but struggle to:

* identify all relevant subtopics
* organize topics into clusters
* understand search intent
* decide which content to create first
* structure internal links
* create a practical content roadmap

Existing SEO platforms can be expensive and overwhelming for beginners.

### Our solution

The user enters a primary topic and optionally a website.

The product researches and analyzes the topic and produces an actionable topical authority structure containing:

* topic hierarchy
* topic clusters
* supporting topics
* search intent
* priority
* internal-linking relationships
* exportable content plan

# 5. Paid Usage Model

The fundamental unit is a **Generation Credit**.

### One credit = one complete topical authority generation.

A generation may internally perform many operations:

* research
* query expansion
* clustering
* intent classification
* prioritization
* linking analysis

The customer sees this as one product operation.

### Paid allowance

**10 generation credits**

### Regeneration

Regeneration consumes another credit.

### Why credits instead of unlimited usage?

Because our price is deliberately low.

Credits give us:

* predictable AI costs
* predictable SEO-data costs
* abuse protection
* sustainable ₹199 pricing
* clear upgrade paths later

Lower-priority or supporting content.

## Frontend

**Next.js + TypeScript**

Reasons:

* full-stack capability
* excellent React ecosystem
* easy deployment
* marketing + dashboard in one application
* good SEO capabilities

---

## UI

**Tailwind CSS + shadcn/ui**

Principles:

* clean
* fast
* desktop-first
* responsive
* minimal dashboard
* results are the visual centerpiece

---

## Database

**PostgreSQL**

Preferably through Supabase for V1.

Use PostgreSQL for:

* users
* projects
* generations
* topics
* usage
* payments
* audit records

---

## Authentication

Supabase Auth or equivalent managed authentication.

We should not implement password management ourselves.

---

## Backend

Start with Next.js server-side APIs/server actions.

Do not introduce microservices in V1.

---

## Background jobs

Generation should be asynchronous.

Initial architecture can use a managed queue/background-job mechanism.

If workload increases:

```text
API
 ↓
Queue
 ↓
Worker
 ↓
Generation Engine
```

---

## Storage

Use object storage for:

* generated PDFs
* temporary export files

Do not store large generated artifacts directly in database rows.

# 19. Data Ownership

Every user-owned resource must contain a reliable ownership relationship.

Example:

```text
User
 ↓
Project
 ↓
Generation
 ↓
Topics
```

Authorization must be enforced server-side.

A user must never be able to access another user's project by changing an ID in a URL or API request.

---

# 20. Security

## Authentication

* secure managed authentication
* email verification
* password reset
* secure sessions
* optional OAuth

## Authorization

Every request must verify:

1. user is authenticated
2. user owns the resource
3. user has permission for the operation
4. user has sufficient credits

---

## Secrets

API keys must exist only on the server.

Never expose:

* AI keys
* SEO-data API keys
* payment secrets
* database service-role keys

to the browser.

---

## Input validation

Validate all API inputs:

* topic length
* URL format
* country
* language
* request body size
* IDs
* export parameters

---

## Output safety

Treat external search/API content as untrusted data.

Never allow retrieved content to directly execute code or override system instructions.

---

# 21. Rate Limiting

Rate limiting occurs at multiple levels.

## Anonymous

Strict limits.

Expensive generation should not be available anonymously.

---

## Free account

One generation entitlement.

Additional API-level protection:

* requests/minute
* requests/hour
* concurrent generations

---

## Paid account

Higher API limits but still bounded by credits.

Example:

```text
20 requests/minute
200 requests/hour
1 active generation
```

These values should be tuned after beta testing.

---

# 22. Generation Protection

Each generation has:

* maximum runtime
* maximum AI calls
* maximum external API calls
* maximum topics
* maximum output size
* maximum estimated cost

If a generation exceeds its budget:

```text
STOP → mark failed → refund credit if appropriate
```

This prevents accidental or malicious cost explosions.

# 25. Failure Handling

If generation fails because of our infrastructure:

**Do not permanently consume the user's credit.**

Example:

```text
Credit = 8

Generation starts
 ↓
Internal failure
 ↓
Generation marked FAILED
 ↓
Credit restored
 ↓
User can retry
```

If the generation successfully completes, the credit remains consumed.

This should be implemented transactionally.

---

# 26. Data Retention

We should follow data minimization.

### Keep

* account information
* projects
* generated maps
* usage records
* payment records
* required security/audit records

### Avoid unnecessary retention of

* raw external search responses
* unnecessary IP history
* temporary API responses
* redundant AI prompts/results
* large temporary files

Temporary generation data should have an expiration policy.

# 41. Founder Rule

The biggest danger is **building too much before proving demand**.

Therefore:

> **V1 is not an SEO platform. V1 is a very good topical-authority generator with excellent economics.**

Our first job is not to beat Ahrefs or Semrush.

Our first job is to make someone say:

> "I would normally spend hours doing this manually. ₹199 is a no-brainer."

Then we find the next problem they want us to solve.

# 42. Immediate Next Step

Before coding the UI, we should finalize four technical/business decisions:

### A. Exactly what constitutes one generation

Define the maximum:

* topics
* clusters
* AI calls
* external data calls
* processing time
* estimated cost

### B. SEO data strategy

Decide whether V1 uses:

* search APIs
* keyword databases
* SERP providers
* third-party SEO data
* our own crawling
* AI-only expansion

This decision has the biggest impact on both **quality and economics**.

### C. Exact database schema

Turn the conceptual tables above into:

* columns
* types
* indexes
* foreign keys
* RLS policies
* retention rules

### D. Exact API contract

Define endpoints such as:

```text
POST   /api/projects
GET    /api/projects
POST   /api/generations
GET    /api/generations/:id
GET    /api/generations/:id/topics
GET    /api/generations/:id/links
POST   /api/exports
GET    /api/usage
POST   /api/webhooks/payment
DELETE /api/account
```

Once those four decisions are locked, we can move directly into **architecture → database → API → UI → implementation** without repeatedly redesigning the product.
